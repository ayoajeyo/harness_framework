## 공통 ADR (AYOCODING 모든 프로젝트 기본값 — 바꿀 이유가 있을 때만 새 ADR로 덮어쓴다)

### ADR-000-1: 빌드 도구 없는 HTML + CSS + 순수 JavaScript
**결정**: React·Next.js 같은 프레임워크와 번들러를 쓰지 않는다.
**이유**: 파일을 열면 그대로 코드가 보여 초보자가 이해·수정하기 쉽다. 빌드 실패가 없다. GitHub Pages 에 바로 올라간다.
**트레이드오프**: 화면이 매우 복잡해지면 코드가 길어진다. → 그때 ADR 로 다시 결정.

### ADR-000-2: 배포는 GitHub Pages
**결정**: `main` 브랜치 push 가 곧 배포.
**이유**: 무료, HTTPS 기본(카메라·위치 권한에 필요), 별도 서버 관리 없음.
**트레이드오프**: 서버 코드를 못 돌린다 → 서버 로직이 필요하면 Supabase Edge Function.

### ADR-000-3: 데이터는 기기 우선, 서버는 필요할 때 Supabase
**결정**: 처음엔 기기(IndexedDB/localStorage)에만 저장. 여러 기기·여러 사람이 같은 데이터를 봐야 할 때 Supabase 를 붙인다.
**이유**: 개인정보가 기기 밖으로 나가지 않는 게 가장 안전하고, 회원가입 없이 바로 쓸 수 있다.
**트레이드오프**: 폰을 바꾸면 데이터 이전이 필요 → 내보내기/가져오기 기능을 v1 에 넣는다.

### ADR-000-4: 사진은 축소해서 저장, 원본은 보관하지 않음
**결정**: 촬영 즉시 긴 변 1600px·JPEG 품질 0.85 로 줄여 저장.
**이유**: 측정에는 충분한 해상도이고, 저장 공간·업로드 비용이 1/5 이하.
**트레이드오프**: 고해상도 원본이 필요한 용도에는 부적합.

### ADR-000-5: 디자인은 네이비 단일 포인트의 심플 스타일
**상태**: 대체됨 (→ ADR-000-11 무채색)
**결정**: `docs/UI_GUIDE.md` 기본값 사용. 프로젝트마다 색을 새로 정하지 않는다.
**이유**: 아요코딩 제품군이 한 회사 제품으로 보이게. 결정 시간 절약.
**트레이드오프**: 개성 있는 비주얼은 포기.

### ADR-000-6: 버전은 네 곳 동시 갱신, 배포는 `/ship` 으로만
**결정**: APP_VERSION · manifest · sw.js CACHE_VERSION · CHANGELOG 를 `/ship` 이 함께 올린다.
**이유**: 하나라도 빠지면 사용자 폰에 이전 화면이 남는 사고가 반복됐다.
**트레이드오프**: 급한 수정도 `/ship` 절차를 거쳐야 한다(약 2분).

### ADR-000-7: 테스트는 계산 로직에만 자동, 화면은 폰 수동 점검표
**결정**: `js/logic/` 은 `node --test` 로 자동 검사. 화면은 `TESTING.md` 의 점검표를 실제 폰에서 손으로 확인.
**이유**: 카메라·터치·인쇄는 자동화 비용이 너무 크다. 로직은 자동화 비용이 거의 없다.
**트레이드오프**: 화면 회귀(예전 버그 재발)를 사람이 잡아야 한다.

### ADR-000-8: 외부 스킬·에이전트는 골라서 저장소에 넣고, 하네스와 겹치는 것은 부를 때만
**결정**: Superpowers 13개(시작 훅·using-superpowers 제외), UI UX Pro Max 1개, Caveman 4개를 `.claude/skills/` 에, claude-code-templates 의 점검 에이전트 3개(a11y·speed·supabase)를 한국어로 옮겨 `.claude/agents/` 에 넣는다. 하네스 흐름과 겹치는 스킬은 `disable-model-invocation: true` 로 사용자가 부를 때만, 점검 에이전트 3개도 부를 때만. 출처·라이선스는 `THIRD_PARTY_NOTICES.md` 와 각 폴더 `LICENSE`.
**이유**: 클라우드 작업 공간은 대화가 끝나면 사라지므로 저장소에 있어야 어느 PC·클라우드에서든 남는다. 통째 설치·시작 훅은 `/feature`·`/fix`·`/ship` 과 부딪히고 외부 최신 코드를 바로 실행한다.
**트레이드오프**: 원본이 바뀌어도 자동으로 안 따라온다(필요하면 다시 복사). 저장소가 약 4MB 커진다.

### ADR-000-9: Graphify(코드 지도)는 설치 안내만 두고, 부를 때만 쓴다
**결정**: 파일을 하네스에 복사하지 않는다. START_HERE.md 에 PC 별 설치 두 줄(`pip install --user graphifyy` → `graphify install`), `.gitignore` 에 `graphify-out/`, CLAUDE.md 에 "`/graphify` 로 부를 때만" 규칙을 둔다.
**이유**: 스킬만으로는 돌지 않고 PC 마다 Python 프로그램이 있어야 한다. `graphify install` 이 최신 스킬을 깔아 주므로, 복사본을 두면 낡은 채 남는다. 설치된 스킬 설명이 "코드 질문이면 먼저 쓰라" 여서 그대로 두면 토큰을 많이 쓴다.
**트레이드오프**: 클라우드 작업 공간에서는 매번 설치해야 한다(Archify 와 같음). 한 파일짜리 작은 앱에서는 얻는 게 적다.

### ADR-000-10: 서버·사업 기능 노하우를 스킬로 (로그인·계정 삭제·Play 구독)
**결정**: 바디샷에서 출시해 본 로그인(이메일·구글·카카오·네이버 서버 함수)·인증 메일(Gmail SMTP)·계정 삭제를 `login-account`, Play 월 구독(서버 확인·구매 확정·체험 중 구독)을 `play-subscription` 스킬로 둔다. 일시정지 방지·고객 문의·AI 서버 함수는 `supabase-safe` 에 몇 줄. 앱 이름·패키지·키 같은 바디샷 전용 값은 넣지 않는다.
**이유**: 이 기능들은 외부 서비스 함정(기본 메일 발송 한도, 3일 안 구매 확정 안 하면 자동 환불, 네이버 검수, 소셜 이메일로 계정 가로채기)이 많아 처음부터 다시 만들면 같은 사고를 반복한다.
**트레이드오프**: 외부 정책·API 버전이 바뀌면 스킬이 낡는다 → 스킬에 "2026-10 기준"·종료 예정 날짜를 적고, 만들 때 공식 문서를 확인한다.

### ADR-000-11: 기본 디자인을 무채색(흰색·검정·회색)으로
**결정**: 포인트 색 네이비 `#1E2A4A` 를 없애고 흰 바탕(`--page` #FFFFFF) + 검정 주 버튼(`--ink` #1D1D1F) + 회색(#6E6E73·#E5E5EA·#F5F5F7)으로 바꾼다. 아이콘은 기본 도형 선 아이콘, 검정·회색만. 빨강·주황·초록은 상태 표시에만. 앱 설치 테마색도 흰색.
**이유**: 사용자가 "색깔이 오히려 피곤하다", "애플·노션 같은 전문가 취향을 벤치마킹하자"(TASTE.md 2026-10-28). 색이 없으면 화면 위계를 크기·굵기·회색 단계로만 내게 되어 더 차분하다.
**트레이드오프**: 페이지와 카드가 둘 다 흰색이라 카드 구분은 테두리(`--line`)에만 기댄다. 이미 만든 앱(바디샷 블루 등)은 그대로 — 바꾸려면 그 앱에서 따로. 앱 고유 색이 필요하면 그 앱 ADR 로 덮어쓴다.
