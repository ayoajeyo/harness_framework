# 로그인 · 계정

> 바디샷(2026-10 기준)에서 실제로 출시해 본 방법이다. 외부 서비스 화면 메뉴 이름은 바뀔 수 있으니, 설정할 때는 공식 문서를 확인한다. 기본 원칙(RLS·키 구분)은 `supabase-safe` 스킬.

## 1. 어떤 로그인을 넣나
| 방법 | 붙이는 법 | 주의 |
|---|---|---|
| 이메일 + 비밀번호 | Supabase 기본 | **인증 메일 발송을 반드시 바꾼다** (2번) |
| 구글 | Supabase Providers → Google | Google Cloud 의 OAuth 동의 화면에 개인정보처리방침 주소 필요 |
| 카카오 | Supabase Providers → Kakao | 이메일(`account_email`)은 **비즈 앱**만 받음 → 전환 전엔 Supabase 에서 "Allow users without an email" 켜기 |
| 네이버 | Supabase 기본 지원 없음 → **서버 함수**(3번) | **검수 전에는 등록한 테스터 아이디만** 로그인됨. 출시 전 검수 요청 |

- 모든 방법의 Redirect URL 에 실제 앱 주소(`https://아이디.github.io/앱/**`)와 로컬 시험 주소를 등록한다.
- 로그인 상태는 `onAuthStateChange` 로 받아 화면을 다시 그린다.
- 시작은 이메일 + 구글 정도로 작게. 카카오·네이버는 사용자가 원할 때 추가(요청하지 않은 기능은 BACKLOG).

## 2. 인증 메일 — Supabase 기본 발송기를 그대로 쓰지 않는다
기본 발송기는 시험용이다. **프로젝트 팀원 주소에만** 보내고, 프로젝트 전체에서 시간당 2통 정도만 보낸다. 그대로 출시하면 다른 사용자는 가입 인증·비밀번호 찾기 메일을 못 받고, 여러 번 누르면 "요청이 너무 잦아요" 로 모두의 가입이 막힌다.

**해결 (사용자가 대시보드에서 직접 — 비밀번호를 채팅·저장소에 쓰지 않게 안내):**
1. 앱 전용 Gmail 계정에 2단계 인증 → `myaccount.google.com/apppasswords` 에서 **앱 비밀번호 16자리**
2. Supabase **Authentication → Emails → SMTP Settings → Enable custom SMTP**: Host `smtp.gmail.com`, Port `465`, Username·Sender = 그 Gmail, Password = 앱 비밀번호
3. **Rate Limits → 메일 발송**: 시간당 30 정도 (Gmail 은 하루 약 500통)
4. **Templates**: 가입 인증·비밀번호 재설정을 한국어로 (`{{ .ConfirmationURL }}` 유지, 끝에 `made by AYOCODING`·문의 주소)
5. 팀원이 아닌 새 주소로 가입해 메일이 오는지 확인 (스팸함 포함)

하루 가입이 수백 건을 넘으면 메일 발송 서비스(예: Brevo)로 옮긴다. 앱 코드는 안 바뀐다. 이 결정은 앱 `docs/ADR.md` 에 적는다.

## 3. 네이버 로그인 서버 함수 (`naver-auth`)
흐름: 앱이 네이버에서 받은 `code`·`state` 를 함수로 보냄 → 함수가 네이버 토큰 교환·프로필(이메일) 확인 → 같은 이메일의 Supabase 계정을 찾거나 만듦 → `generateLink({ type: "magiclink" })` 의 `hashed_token` 을 돌려줌 → 앱이 `supabase.auth.verifyOtp({ token_hash, type: "magiclink" })` 로 로그인.
- `NAVER_CLIENT_SECRET` 은 Supabase **Edge Functions → Secrets** 에만. Client ID 는 공개값.
- 네이버 앱 설정에서 이메일을 **필수** 제공 정보로.

### 계정 가로채기 막기 (반드시)
소셜 로그인의 이메일만 믿고 기존 계정에 연결하면, 남이 같은 이메일로 다른 서비스 계정을 만들어 들어올 수 있다.
- 처음 연결할 때 네이버 고유번호를 **`app_metadata`**(사용자가 못 바꾸는 칸)에 적고, 다음부터 번호가 다르면 거절.
- 이미 다른 방법(이메일·구글·카카오)으로 가입해 **인증까지 마친** 계정에는 자동 연결하지 않는다 → "처음 가입한 방법으로 로그인해 주세요".
- 같은 이메일로 **인증 안 된** 이메일 가입이 먼저 있었다면(남이 미리 만들었을 수 있음) 그 비밀번호를 무작위로 바꾸고 소셜 계정으로 확정.

## 4. 계정 삭제 (`delete-account`) — Google Play 필수
Play 정책: 앱 안에서 계정과 자료를 지울 수 있어야 하고, **앱 밖 웹 페이지**에서도 삭제 방법을 안내해야 한다(Play Console 에 주소 등록).
- 함수는 요청의 로그인 토큰으로 `admin.auth.getUser(jwt)` → **본인 것만** 지운다.
- 순서: **사진 파일(Storage) 먼저 → 계정 삭제**. 사진 삭제가 하나라도 실패하면 계정을 지우지 않는다(주인 없는 사진이 남지 않게, 다시 시도 가능). 표의 자료는 `on delete cascade` 로 계정과 함께 지워지게 설계(`supabase-safe`).
- Storage `list` 는 1000개씩·하위 폴더까지 따라가며 모은다(폴더는 `id` 가 없음).
- 앱 안 삭제 확인 창과 웹 삭제 안내 페이지에 **"Play 구독은 계정을 지워도 자동 해지되지 않아요 — Play 스토어에서 해지하세요"** 를 넣는다 (`play-subscription`).
- 개인정보처리방침의 "파기" 항목과 맞춘다 (`korean-privacy`).

## 5. 서버 함수 공통
- CORS 허용 주소는 실제 앱 주소만 (`_cors.ts` 같은 공용 파일 하나에서 관리).
- 관리자 키는 함수 환경변수에서만 읽는다. 새 방식(`SUPABASE_SECRET_KEYS`)을 먼저, 없으면 `SUPABASE_SERVICE_ROLE_KEY`.
- 오류 응답은 화면에 그대로 보여 줄 한국어 문장으로 (`ux-writing`). `console.error` 에 이메일·이름을 남기지 않는다.

## 6. 출시 전 점검
- [ ] 팀원이 아닌 새 주소로 가입 인증·비밀번호 재설정 메일이 온다
- [ ] 각 소셜 로그인이 **실제 앱 주소**에서 된다 (로컬만 확인하지 않기)
- [ ] 네이버 검수 요청 완료 (안 하면 테스터만 로그인)
- [ ] 카카오 비즈 앱 전환 여부와 이메일 없는 계정 처리
- [ ] 앱 안 계정 삭제 + 웹 삭제 안내 페이지, Play Console 에 주소 등록
- [ ] 개인정보처리방침에 수집 항목(이메일·이름·소셜 고유번호)·보관 위치·삭제 방법
- [ ] Play Console 데이터 보안 양식에 계정 정보 반영

이 작업은 로그인·삭제가 걸려 있어 `plan-gate` 대상이다 — 계획서 승인 뒤 만든다.
