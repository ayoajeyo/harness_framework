# 저장 형식 바꾸기 (기존 자료 지키기)

앱을 이미 쓰는 사람의 폰·서버에는 **예전 형식 자료**가 남아 있다. 새 코드는 예전 자료를 그대로 읽어야 한다.
한 번 잃은 자료는 되돌릴 수 없으므로, 이 작업은 `plan-gate`(계획 승인) 대상이다.

## 1. 절대 바꾸지 않는 것 (CRITICAL)
- IndexedDB **데이터베이스 이름·저장소(store) 이름**, localStorage **키 이름**, 서버 **표·칸 이름**, 앱 패키지 이름.
  바꾸면 기존 자료가 "없는 것"처럼 보인다. 이름이 마음에 안 들어도 그대로 두고, 화면에 보이는 이름만 바꾼다.
- 이 앱의 바꾸면 안 되는 이름은 CLAUDE.md "이 프로젝트만의 규칙" 에 CRITICAL 로 적어 둔다.

## 2. 순서
1. `docs/DATA.md` 에 **먼저** 적는다: 새 칸 이름·형식·등급(S1~S3)·삭제 시점, 그리고 "예전 자료에는 없음 → 어떻게 보임".
2. 예전 자료를 읽는 계산은 `js/logic/` 에 두고 **예전 형식 테스트를 먼저** 쓴다 (`test-driven-development`).
3. 코드는 **더하기만**: 새 칸을 추가하고, 예전 칸은 지우지 않는다. 의미를 바꿔야 하면 새 이름의 칸을 만든다.
4. `browser-check` 로 예전 자료가 섞인 상태를 실제로 연다.
5. `reviewer` + `privacy-guard` 검토 → 커밋.

## 3. 읽기 규칙
| 상황 | 처리 |
|------|------|
| 새 칸이 없는 예전 자료 | 오류 없이 **'모름'·'없음'** 으로 보이게 (`x.how == null ? "모름" : …`). 지어내지 않는다 |
| 배열 안 빈 값(null) | 모든 반복문에서 `if (!p) return;` — 좌표·사진 목록에 빈 칸이 있을 수 있다 |
| 크기가 다른 예전 좌표 | 저장할 때 **기준 크기(가로×세로)** 를 함께 적고, 다르면 비율로 환산. 환산한 값은 표시해 둔다 |
| 숫자 단위가 바뀜 | 칸 이름이나 함께 적은 단위로 구분 (°·%·px). 섞어서 평균 내지 않는다 |
| 다시 저장(수정) | 처음 자동으로 정해진 값(수정 전 점, 촬영 조건 등)은 **처음 것을 유지**. 수정 저장이 덮어쓰지 않게 |

## 4. 저장 규칙
- 새 칸에는 **어느 버전에서 저장했는지**(앱 버전)를 함께 남기면 나중에 원인 분석이 쉽다.
- 사진 크기·화질을 바꾸면 기기 저장 공간과 서버 용량이 바뀐다 → DATA.md 와 계획서에 크기(px·화질)를 적는다.
- 개인정보가 들어가는 새 칸은 등급·삭제 시점·동의 조건을 정하기 전에 저장하지 않는다 (`korean-privacy`).
- 회원 삭제·동의 철회 때 새 칸(특히 사진)도 함께 지워지는지 확인한다.

## 5. 서버(Supabase) 표를 바꿀 때
- SQL 파일은 번호를 붙여 새로 만든다(`supabase/vNNN_무엇.sql`). 예전 파일을 고치지 않는다.
- `add column … default …` 처럼 기존 행이 깨지지 않는 방식만. 칸 삭제·이름 변경·형식 변경은 계획 승인 + 백업 뒤.
- 적용 전 `supabase-checker` 로 점검, 적용은 사용자 확인 뒤 (`supabase-safe`).

## 6. 확인 체크리스트
- [ ] DATA.md 에 새 칸과 "예전 자료에선 어떻게 보이나" 를 적었다
- [ ] 바꾸면 안 되는 이름을 하나도 안 바꿨다
- [ ] 예전 형식·새 형식·빈 값 자료로 자동 테스트가 있다
- [ ] `browser-check` 로 예전 자료가 섞인 화면·내보내기를 열어 봤다
- [ ] 다시 저장해도 처음 값이 지켜진다
- [ ] 삭제·동의 철회 때 새 칸도 지워진다
